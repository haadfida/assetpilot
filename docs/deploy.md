# Deploying AssetPilot

The setup is three free-tier pieces, and you create each of them by hand. Nothing in this repo creates
cloud resources for you.

| Piece | Where | Config in the repo |
| --- | --- | --- |
| PostgreSQL | Supabase (free project) | `config/database.yml` reads `DATABASE_URL` |
| Rails API (+ `/mcp`) | Render web service (free plan) | `render.yaml` |
| React frontend | Vercel (Hobby) | `frontend/vercel.json`, `VITE_API_URL` |

**No Anthropic key is needed on the server.** Without one, the app serves the 8 recorded prompts in replay
mode. Visitors who want live answers paste their own key in the UI settings (BYOK). The key goes in
the `x-anthropic-key` header straight to the API and is never stored. Do not set `ANTHROPIC_API_KEY` on
Render; it is only read in development anyway.

> **Cold starts.** Render's free web services spin down after about 15 minutes without traffic. The first
> request after that wakes the service, which takes **roughly 30-60 seconds** (sometimes longer). Until
> then the UI shows the replay catalog loading or a slow first run. Before a demo, open
> `https://<your-service>.onrender.com/up` and wait for `200`. Supabase free projects also **pause after
> a week of inactivity**; resume them from the Supabase dashboard.

## 0. Check it locally first

```sh
docker-compose up -d db
script/production_check
```

This boots the app the way Render does. It uses `RAILS_ENV=production`, no Anthropic key, no master key,
no dev/test gems, a dummy `SECRET_KEY_BASE` and the `render.yaml` start command, all against a throwaway
local database (`assetpilot_production_check`). It then checks health, a replay run streamed end to end,
the 422 for an unknown prompt, CORS, and the read-only MCP endpoint with its host guard. It must print
`PRODUCTION BOOT CHECK PASSED`.

## 1. Supabase: database and connection string

1. Go to https://supabase.com/dashboard and choose **New project**. Pick a name (e.g. `assetpilot`) and a
   region near where you'll run Render (e.g. Frankfurt, `eu-central-1`). Set a database password and save it.
2. When the project is ready, click **Connect** (top bar). Under **Connection string**, choose **Session
   pooler**. Copy the URI. It looks like:

   ```
   postgresql://postgres.<project-ref>:<YOUR-PASSWORD>@aws-0-<region>.pooler.supabase.com:5432/postgres
   ```

   Replace `[YOUR-PASSWORD]` with the password from step 1 (URL-encode any special characters) and append
   `?sslmode=require`.

   - Use the **session pooler** (port 5432), not the "Direct connection". The direct host is IPv6-only on
     the free plan, and Render can't reach IPv6.
   - If you use the **transaction pooler** (port 6543) instead, also set `DB_PREPARED_STATEMENTS=false`
     on Render.

You don't need to create any tables. The first Render boot runs the migrations and seeds the demo data.

## 2. Render: the API from the Blueprint

1. Push the repo to GitHub (it is `haadfida/assetpilot`) with `render.yaml` on `main`.
2. In https://dashboard.render.com, go to **New** > **Blueprint**, connect GitHub, and pick the repo. Render
   reads `render.yaml` and proposes one web service, `assetpilot-api`, on the **Free** plan.
3. Render asks for the variables marked `sync: false`. Set them:

   | Variable | Value |
   | --- | --- |
   | `DATABASE_URL` | the Supabase session-pooler URI from step 1, with `?sslmode=require` |
   | `CORS_ORIGINS` | your Vercel URL, e.g. `https://assetpilot.vercel.app`. If you don't know it yet, put a placeholder and come back after step 4. Comma-separate several origins. |
   | `MCP_ALLOWED_HOSTS` | the Render host name, e.g. `assetpilot-api.onrender.com`. Render shows it once the service exists; if the name was taken it has a suffix. |
   | `MCP_TOKEN` | optional. If you set it, `/mcp` requires `Authorization: Bearer <token>`. Leave it empty for an open read-only endpoint. |

   `SECRET_KEY_BASE` is generated by Render. `RAILS_ENV`, `BUNDLE_WITHOUT`, `RAILS_MAX_THREADS` and
   `RAILS_LOG_LEVEL` come from the Blueprint.
4. Click **Apply**. The build runs `bundle install` (Render's native Ruby runtime picks up
   `.ruby-version`, 3.2.3; no Dockerfile is needed). The start command then runs:

   ```sh
   bundle exec rails db:migrate && bundle exec rails db:seed_if_empty && bundle exec puma -C config/puma.rb
   ```

5. Check it (allow for the cold start):

   ```sh
   API=https://assetpilot-api.onrender.com
   curl -s $API/up                                  # 200
   curl -s $API/api/agent/replays                   # 8 prompts
   curl -s -XPOST $API/api/agent/runs -H 'content-type: application/json' \
        -d '{"prompt":"What breaks if DB-Server goes down?"}'      # "mode":"replay"
   ```

## 3. Seeds

Seeding happens **automatically on the first boot**. `db:seed_if_empty` loads the deterministic demo data
(506 assets, 60 people, 9 locations, 12 services, 212 dependency edges) only when the `assets` table is
empty, so restarts and redeploys never wipe it.

To **reset** the demo data later (for example after visitors checked things out with their own keys), run
`bin/rails db:seed`. It truncates and rebuilds the domain tables. Pick one of these ways to run it:

- **From your machine** (works on the free plan): run
  `DATABASE_URL='<supabase uri>' RAILS_ENV=production SECRET_KEY_BASE=dummy bin/rails db:seed`
- **Render Shell** (paid instance types only): open the service, go to **Shell**, and run `bin/rails db:seed`.
- **Render one-off job** (paid): create a job for the service with the start command `bin/rails db:seed`
  (from the dashboard or Render's API). It runs with the service's environment.

## 4. Vercel: the frontend

1. In https://vercel.com/new, import the same GitHub repo.
2. Set **Root Directory** to `frontend`. Vercel picks up `frontend/vercel.json` (Vite, `npm ci`,
   `npm run build`, output `dist`).
3. Under **Environment Variables**, add `VITE_API_URL` = `https://assetpilot-api.onrender.com` (your
   Render URL, with no trailing slash). It is read at build time, so changing it later needs a redeploy.
4. Click **Deploy** and note the production URL (e.g. `https://assetpilot.vercel.app`).
5. Back on Render, set `CORS_ORIGINS` to that URL (Environment, then **Save, rebuild and deploy**).
   Preview deployments get their own `*.vercel.app` URLs. Add any you want to use to `CORS_ORIGINS`;
   others will see CORS errors.
6. Open the Vercel URL and click "What breaks if DB-Server goes down?". The graph should draw. The first
   click after an idle period waits for Render's cold start.

The browser calls the Render API directly, so the agent's Server-Sent Events stream isn't buffered by a proxy.

## 5. Optional: MCP over HTTP from Claude Code

The deployed `/mcp` endpoint is read-only: the mutating tools aren't listed unless `MCP_ALLOW_WRITES=1`.

```sh
claude mcp add --transport http assetpilot-cloud https://assetpilot-api.onrender.com/mcp
# with MCP_TOKEN set:
claude mcp add --transport http assetpilot-cloud https://assetpilot-api.onrender.com/mcp --header "Authorization: Bearer <token>"
```

A request whose `Host` isn't in `MCP_ALLOWED_HOSTS` gets a 403.

## Checklist of what you have to do

- [ ] `script/production_check` passes locally.
- [ ] Supabase project created and session-pooler URI copied (`?sslmode=require`).
- [ ] Render Blueprint applied, with `DATABASE_URL`, `CORS_ORIGINS` and `MCP_ALLOWED_HOSTS` set.
- [ ] `/up` returns 200 and `/api/agent/replays` lists 8 prompts (the first boot seeded the database).
- [ ] Vercel project with root `frontend` and `VITE_API_URL` set to the Render URL, deployed.
- [ ] `CORS_ORIGINS` on Render updated to the Vercel URL, then redeployed.
- [ ] Before a demo, warm the Render service by hitting `/up` (free-plan cold start).
